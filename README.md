# Philadelphia Parking Analytics

Консольное Java-приложение для анализа парковочных нарушений, жилой недвижимости и численности населения по ZIP-кодам Филадельфии.

Приложение объединяет три источника данных, загружает их по требованию, рассчитывает показатели на уровне ZIP-кодов и позволяет исследовать связь между зарегистрированными парковочными нарушениями и средней рыночной стоимостью недвижимости.

Отчёт по дипломному проекту находится в [`report.pdf`](report.pdf); его текстовая исходная версия — [`docs/REPORT.md`](docs/REPORT.md).

## Возможности

После запуска приложение предоставляет меню из семи пунктов:

| Пункт | Операция | Результат |
|---:|---|---|
| `0` | Выход | Завершение приложения |
| `1` | Общая численность населения | Сумма населения по всем ZIP-кодам |
| `2` | Штрафы на душу населения | Сумма штрафов на одного жителя для каждого ZIP-кода |
| `3` | Средняя рыночная стоимость | Средняя `market_value` объектов недвижимости для заданного ZIP-кода |
| `4` | Средняя жилая площадь | Средняя `total_livable_area` для заданного ZIP-кода |
| `5` | Рыночная стоимость на душу населения | Сумма рыночных стоимостей, делённая на население ZIP-кода |
| `6` | Дополнительный анализ | Нарушения на 1 000 жителей, средняя стоимость недвижимости и корреляция Спирмена |

Для пунктов 3–5 программа запрашивает пятизначный ZIP-код.

## Технологии

- **Java 17** — язык и целевая версия байт-кода.
- **Spring Boot 4.1.2** — запуск приложения и внедрение зависимостей.
- **Apache Maven** — сборка, зависимости и тестирование.
- **Apache Commons CSV 1.14.1** — чтение CSV-файлов.
- **json-simple 1.1.1** — чтение JSON-файла парковочных нарушений.
- **JUnit 5 и Mockito** через `spring-boot-starter-test` — автоматизированные тесты.

Для сборки и воспроизводимого запуска используйте JDK 17: в `pom.xml` заданы `java.version=17` и `maven.compiler.release=17`. Перед запуском проверьте, что `java` из `PATH` указывает на нужную JVM:

```bash
java -version
```

## Входные данные

Приложение принимает три файла. Они передаются как аргументы командной строки; пути могут быть абсолютными или относительными к текущему рабочему каталогу.

### Парковочные нарушения: CSV или JSON

Формат выбирается первым аргументом запуска.

**CSV (`parking.csv`)** — файл без строки заголовков. Каждая запись должна содержать ровно семь полей в следующем порядке:

1. `date` — дата и время нарушения;
2. `fine` — сумма штрафа;
3. `violation` — тип нарушения;
4. `plate_id` — обезличенный идентификатор автомобиля;
5. `state` — штат регистрации автомобиля;
6. `ticket_number` — идентификатор квитанции;
7. `zip_code` — ZIP-код места нарушения.

CSV разбирается Apache Commons CSV, поэтому поля в кавычках могут содержать запятые.

**JSON (`parking.json`)** — корневой элемент должен быть массивом объектов с полями `date`, `fine`, `violation`, `plate_id`, `state`, `ticket_number` и `zip_code`.

Штат приводится к верхнему регистру. ZIP-код нормализуется до первых пяти цифр. Некорректные отдельные записи пропускаются; синтаксически некорректный JSON или корневой элемент, не являющийся массивом, приводит к ошибке чтения.

### Недвижимость (`properties.csv`)

CSV-файл должен содержать строку заголовков. Обязательные колонки:

- `zip_code`;
- `market_value`;
- `total_livable_area`.

Позиция колонок не фиксирована: reader находит их по именам заголовков. Обработка `market_value` и `total_livable_area` независима: некорректное значение одного поля не исключает корректное значение другого из соответствующего расчёта. Строка, в которой оба показателя некорректны или отсутствуют, не создаёт полезной записи для аналитики.

Используется Apache Commons CSV, поэтому значения в кавычках могут содержать запятые.

### Население (`population.txt`)

Каждая строка содержит ZIP-код и численность населения, разделённые пробелом или табуляцией:

```text
19102 4705
19103 21908
19104 51808
```

Некорректные строки пропускаются. Повторяющиеся ZIP-коды суммируются на аналитическом уровне.

### Нормализация ZIP-кодов

Для сопоставления источников приложение использует первые пять символов ZIP-кода. Эти пять символов должны быть цифрами. Дополнительные символы после них не влияют на нормализованный код. Значение, которое нельзя нормализовать, не участвует в расчётах, связанных с ZIP-кодом.

## Расчёты

### 1. Общая численность населения

Складываются все корректно прочитанные значения населения:

$$
P_{\mathrm{total}} = \sum_z P_z
$$

Повторяющиеся строки одного ZIP-кода сначала суммируются в общий показатель этого ZIP-кода, а затем входят в общую сумму.

### 2. Штрафы на душу населения

Для ZIP-кода вычисляется:

$$
F_z = \frac{\sum Fine_z}{P_z}
$$

Учитываются только парковочные нарушения со штатом регистрации `PA`, известным ZIP-кодом и числовой суммой штрафа. ZIP-коды с нулевой суммой штрафов, нулевым населением или отсутствующие в файле населения в результат не включаются.

Результаты выводятся в порядке возрастания ZIP-кодов. Значение имеет ровно четыре знака после запятой; используется усечение в сторону нуля (`RoundingMode.DOWN`), а не округление до ближайшего значения.

### 3. Средняя рыночная стоимость

Для заданного ZIP-кода:

$$
M_z = \frac{\sum_{i=1}^{n} MarketValue_i}{n}
$$

В числитель и знаменатель входят только записи с корректным значением `market_value`. Результат выводится целым числом с отбрасыванием дробной части. Если подходящих объектов нет, выводится `0`.

### 4. Средняя жилая площадь

Для заданного ZIP-кода:

$$
A_z = \frac{\sum_{i=1}^{n} LivableArea_i}{n}
$$

Используются только записи с корректным значением `total_livable_area`. Результат выводится целым числом с отбрасыванием дробной части. Если подходящих объектов нет, выводится `0`.

Для команд 3 и 4 применяется паттерн Strategy: `AverageMarketValueStrategy` и `AverageLivableAreaStrategy` реализуют общий контракт `PropertyAverageStrategy`.

### 5. Совокупная рыночная стоимость на душу населения

Для заданного ZIP-кода:

$$
C_z = \frac{\sum MarketValue_z}{P_z}
$$

В числителе находится сумма всех валидных рыночных стоимостей объектов ZIP-кода, в знаменателе — население этого ZIP-кода. Дробная часть отбрасывается. Если ZIP-код некорректен или отсутствует в источниках, население равно нулю либо сумма рыночных стоимостей равна нулю, возвращается `0`.

### 6. Дополнительный анализ: нарушения и стоимость недвижимости

Дополнительный анализ использует **все три источника данных**.

Для каждого ZIP-кода, где население положительно и имеется хотя бы одно корректное значение `market_value`, рассчитываются:

**Количество нарушений на 1 000 жителей**

$$
V_z = \frac{N_z}{P_z} \times 1000
$$

где $N_z$ — количество прочитанных парковочных нарушений с нормализованным ZIP-кодом. Учитываются все штаты регистрации автомобиля. Если для подходящего ZIP-кода нет ни одной записи о нарушении, $N_z = 0$.

**Средняя рыночная стоимость недвижимости**

$$
M_z = \frac{\sum_{i=1}^{n} MarketValue_i}{n}
$$

В знаменатель входят только валидные значения `market_value`.

По рассчитанным значениям $V_z$ и $M_z$ вычисляется коэффициент ранговой корреляции Спирмена. Значения сортируются по возрастанию, совпадающим значениям назначаются средние ранги, затем определяется корреляция Пирсона между рангами. Коэффициент округляется до четырёх знаков после запятой.

Корреляция не определяется, если пригодных ZIP-кодов меньше двух или один из ранговых рядов не имеет вариации. В этом случае приложение выводит отдельное сообщение.

Коэффициент Спирмена описывает направление и силу монотонной связи между показателями. Он не означает причинно-следственную зависимость и сам по себе не является проверкой статистической значимости: проект не рассчитывает p-value или доверительный интервал.

## Загрузка данных и кеширование

При запуске приложение проверяет, что все три входных файла существуют и доступны для чтения. Содержимое файлов при этом не разбирается.

Данные загружаются **лениво**, только когда пользователь выбирает команду, которой нужен соответствующий источник:

| Команда | Загружаемые источники |
|---:|---|
| 1 | Население |
| 2 | Парковочные нарушения и население |
| 3 | Недвижимость |
| 4 | Недвижимость |
| 5 | Недвижимость и население |
| 6 | Все три источника |

`DataLoadingSession` запоминает успешно загруженные источники и не читает их повторно в пределах одного запуска. При последующем запросе новой комбинации источников к сессии добавляются только отсутствующие данные.

`DataLoadingService` выбирает режим чтения по суммарному размеру запрошенных файлов. Если запрошено более одного файла и их суммарный размер не меньше 5 MiB, файлы читаются параллельно с использованием `ExecutorService` и `CompletableFuture`; в остальных случаях применяется последовательное чтение. Порог 5 MiB является эвристикой реализации, а не результатом универсального бенчмарка.

Результаты расчётов мемоизируются в `ComputationCache`, основанном на `ConcurrentHashMap`. Кеширование используется для всех шести аналитических операций, включая дополнительный анализ.

## Архитектура

Проект разделён на слои с независимой ответственностью:

| Пакет | Назначение |
|---|---|
| `ru.ibs.diploma` | Точка входа `Main` и запуск Spring Boot |
| `ru.ibs.diploma.config` | Проверка CLI-конфигурации и настройка инфраструктурных Spring-компонентов |
| `ru.ibs.diploma.ui` | Интерактивное меню и локализация пользовательских сообщений |
| `ru.ibs.diploma.application` | Координация команд и выбор необходимых источников |
| `ru.ibs.diploma.datamanagement` | Загрузка файлов и преобразование CSV/JSON/TXT в предметные модели |
| `ru.ibs.diploma.processor` | Агрегация, аналитические расчёты, стратегии и кеш |
| `ru.ibs.diploma.data` | Модели данных и контейнеры результатов |
| `ru.ibs.diploma.exception` | Исключения валидации CLI и чтения данных |
| `ru.ibs.diploma.logging` | Абстракция и файловая реализация журнала |

Парковочные данные читаются через общий контракт `ParkingDataReader`, поэтому аналитический слой получает одинаковые предметные объекты независимо от того, выбран CSV или JSON.

Spring управляет компонентами инфраструктуры и пользовательского интерфейса. Прикладной фасад `AnalyticsCommandService` создаётся в CLI-сценарии из внедрённых зависимостей, а `AnalyticsService` формируется для соответствующего набора уже загруженных данных.

## Локализация и журналирование

Поддерживаются английский и русский языки:

- `src/main/resources/i18n/messages.properties`;
- `src/main/resources/i18n/messages_ru.properties`.

Локаль выбирается по локали JVM. Для неподдерживаемого языка используется базовый английский bundle.

Журнал создаётся или дополняется в UTF-8. Каждая запись содержит Unix timestamp в миллисекундах и текст события. Записываются старт приложения с аргументами, открытие файлов, введённые команды и ZIP-коды для команд 3–5. Файловый logger использует режим append и синхронизирует запись строк.

## Сборка и запуск

Из корневого каталога проекта выполните:

```bash
mvn clean package
```

Spring Boot Maven Plugin настраивает упаковку приложения в исполняемый JAR с зависимостями. Имя артефакта задано как `diploma.jar`; после успешной сборки он должен находиться в `target/diploma.jar`.

Пример запуска с CSV-файлом парковочных нарушений:

```bash
java -jar target/diploma.jar csv ./parking.csv ./properties.csv ./population.txt ./app.log
```

Пример запуска с JSON-файлом парковочных нарушений:

```bash
java -jar target/diploma.jar json ./parking.json ./properties.csv ./population.txt ./app.log
```

Порядок пяти аргументов фиксирован:

```text
<csv|json> <parking-file> <properties-file> <population-file> <log-file>
```

Формат должен быть строго `csv` или `json` в нижнем регистре. Если число аргументов, формат или доступность входного файла некорректны, приложение выводит локализованную ошибку и завершает CLI-сценарий.

## Тестирование и Javadoc

Тесты написаны на JUnit 5, используются Mockito и временные каталоги JUnit. В проекте находятся 15 тестовых классов и 26 методов `@Test`, покрывающих:

- проверку CLI-аргументов и файлов;
- чтение CSV, JSON и TXT;
- поиск заголовков недвижимости по именам и независимый разбор числовых полей;
- ленивую загрузку и выбор требуемых источников;
- расчёты аналитических показателей и правила усечения;
- дополнительный анализ, включая ZIP-код с нулём нарушений и совпадающие значения при ранжировании;
- неопределённую корреляцию на выборке из одного ZIP-кода;
- повторное использование результатов кеша и однократное вычисление при конкурентных запросах;
- локализацию и файловое журналирование.

Запуск тестов:

```bash
mvn test
```

Генерация Javadoc:

```bash
mvn javadoc:javadoc
```

Сборка проекта также содержит конфигурацию Maven Javadoc Plugin для генерации HTML-документации и Javadoc JAR в фазе `package`.

## Границы текущей версии

Текущая реализация является консольным приложением, работающим с файлами. В проекте нет REST API, базы H2 или другого постоянного хранилища. Данные и результаты кешируются только в памяти в течение текущего запуска.

Архив исходников сам по себе не содержит собранного `target/diploma.jar` и сгенерированного набора HTML/Javadoc-артефактов: они создаются командами Maven, приведёнными выше.
